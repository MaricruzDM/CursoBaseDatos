Antes de escribir una sola línea de SQL, necesitas diseñar tu base de datos. El modelado es como crear los planos de una casa antes de construirla. En esta unidad aprenderás a planificar la estructura de tus datos de forma visual y organizada.

🏠 Analogía: Construir una casa

No empiezas a pegar ladrillos sin planos. Primero un arquitecto dibuja el diseño (modelo conceptual), luego un ingeniero calcula las estructuras (modelo lógico), y finalmente el maestro de obra lo construye (modelo físico). Con las bases de datos es igual.

3.1 Diagrama Entidad-Relación (ER)

📄 Definición

El Diagrama Entidad-Relación (DER) es una representación gráfica que muestra las entidades (cosas del mundo real), sus atributos (características) y las relaciones entre ellas. Fue propuesto por Peter Chen en 1976.

Componentes del diagrama ER

Componente Símbolo Descripción Ejemplo
Entidad Rectángulo Objeto del mundo real sobre el que se almacena información ALUMNO, MATERIA, PROFESOR
Atributo Á“valo/Elipse Característica de una entidad Nombre, Edad, Matrícula
Relación Rombo/Diamante Asociación entre dos o más entidades "cursa", "imparte", "pertenece"
Llave primaria Atributo subrayado Atributo que identifica de forma única Matrícula, RFC
Línea Línea recta Conecta entidades con relaciones y atributos —

3.2 Las Entidades y el Manejo de Relaciones

Tipos de Entidades

📄 Entidad fuerte

Existe por sí misma, no depende de otra entidad para existir. Tiene su propia llave primaria.

Ejemplo: ALUMNO, PROFESOR, MATERIA

📄 Entidad débil

No puede existir sin una entidad fuerte asociada. Su llave primaria incluye la llave de la entidad fuerte de la que depende.

Ejemplo: DEPENDIENTE (no existe sin EMPLEADO), DETALLE_FACTURA (no existe sin FACTURA)

Cardinalidad de las Relaciones

La cardinalidad indica cuántas instancias de una entidad pueden asociarse con instancias de otra. Es fundamental para diseñar correctamente las tablas.

Cardinalidad Símbolo Significado Ejemplo
Uno a Uno (1:1) 1 — 1 Cada registro de A se asocia con máximo uno de B, y viceversa PERSONA â†” PASAPORTE (una persona tiene un pasaporte)
Uno a Muchos (1:N) 1 — * Un registro de A se asocia con muchos de B, pero cada B solo con uno de A DEPARTAMENTO â†’ EMPLEADOS (un depto. tiene muchos empleados)
Muchos a Muchos (M:N) * — * Múltiples registros de A se asocian con múltiples de B ALUMNO â†” MATERIA (un alumno cursa muchas materias, una materia tiene muchos alumnos)

🔬 Analogías de cardinalidad

  • 1:1 — Como una persona y su INE: cada quien tiene exactamente una.
  • 1:N — Como una madre y sus hijos: una madre puede tener varios hijos, pero cada hijo tiene solo una madre biológica.
  • M:N — Como estudiantes y clubes: un estudiante puede estar en varios clubes, y un club tiene varios estudiantes.

⚠️ Importante: Resolver relaciones M:N

Las relaciones muchos a muchos no se pueden implementar directamente en una base de datos relacional. Se resuelven creando una tabla intermedia (tabla puente o tabla de unión) que contiene las llaves foráneas de ambas tablas.

✅ Ejemplo: Resolver una relación M:N

Problema: ALUMNO cursa MATERIA (muchos a muchos)

3.3 Modelo Lógico y Físico

El diseño de una base de datos pasa por tres niveles de abstracción, cada uno con un propósito diferente:

Nivel Â¿Qué describe? Â¿Quién lo hace? Herramienta
Modelo Conceptual QUÁ‰ datos necesitamos (entidades, relaciones, sin detalles técnicos) Analista + cliente Diagrama ER básico
Modelo Lógico CÁ“MO se organizan los datos (tablas, columnas, tipos de dato, llaves, relaciones) Diseñador de BD Diagrama ER detallado / Modelo relacional
Modelo Físico DÁ“NDE y cómo se almacenan (índices, particiones, espacios en disco, motor de BD específico) DBA Scripts SQL, configuración del DBMS

✅ Ejemplo de los tres niveles para "Alumno"

Conceptual: "Necesitamos almacenar información de alumnos: su nombre, matrícula y qué carrera estudian."

Lógico:

Tabla: ALUMNOS
  - Matricula: VARCHAR(10), PK
  - Nombre: VARCHAR(50), NOT NULL
  - Apellido: VARCHAR(50), NOT NULL
  - CarreraID: INT, FK â†’ CARRERAS.CarreraID

Físico:

CREATE TABLE Alumnos (
    Matricula VARCHAR(10) NOT NULL,
    Nombre VARCHAR(50) NOT NULL,
    Apellido VARCHAR(50) NOT NULL,
    CarreraID INT NOT NULL,
    CONSTRAINT PK_Alumnos PRIMARY KEY (Matricula),
    CONSTRAINT FK_Carrera FOREIGN KEY (CarreraID)
        REFERENCES Carreras(CarreraID)
) ENGINE=InnoDB;

CREATE INDEX idx_carrera ON Alumnos(CarreraID);

🔬 Analogía: Niveles de diseño de una casa

  • Conceptual: "Quiero una casa con 3 recámaras, 2 baños y jardín" (el cliente dice qué necesita)
  • Lógico: Plano arquitectónico con medidas, distribución, dónde van las ventanas (el arquitecto diseña)
  • Físico: Plano estructural con tipo de cimentación, calibre de varillas, grosor de muros (el ingeniero detalla la construcción)

3.4 El Diccionario de Datos como Herramienta de Documentación

📄 Definición

El diccionario de datos es un documento que describe de forma detallada cada elemento de la base de datos: tablas, columnas, tipos de dato, restricciones, relaciones y reglas de negocio. Es la "documentación técnica" de tu BD.

🔬 Analogía

Es como el manual de usuario de un equipo electrónico. Así como el manual te dice qué hace cada botón, el voltaje que necesita y las especificaciones, el diccionario de datos te dice qué significa cada campo, qué valores acepta y cómo se relaciona con otros.

✅ Ejemplo: Diccionario de datos para tabla ALUMNOS

Campo Tipo de Dato Tamaño Restricción Descripción
Matricula VARCHAR 10 PK, NOT NULL Identificador único del alumno. Formato: AXXXX

Apellido VARCHAR 50 NOT NULL Apellido paterno del alumno
Email VARCHAR 100 UNIQUE Correo electrónico institucional
FechaNac DATE - NOT NULL Fecha de nacimiento (AAAA-MM-DD)
CarreraID INT - FK, NOT NULL Referencia a la tabla CARRERAS
Activo BOOLEAN - DEFAULT TRUE Indica si el alumno está activo o dado de baja

💡 Â¿Por qué es importante?

  • Facilita la comunicación entre desarrolladores y analistas
  • Sirve como referencia cuando alguien nuevo se integra al proyecto
  • Ayuda a mantener consistencia cuando la BD crece
  • Es requisito en muchas metodologías de desarrollo

3.5 Normalización (1FN, 2FN y 3FN)

📄 Definición

La normalización es un proceso de organización de tablas que busca eliminar la redundancia (datos repetidos) y las anomalías (problemas al insertar, actualizar o borrar datos). Se aplica en etapas progresivas llamadas "formas normales".

🔬 Analogía

Es como organizar un clóset desordenado. Primero sacas todo y lo pones en orden (1FN). Luego separas la ropa por tipo: camisas en un cajón, pantalones en otro (2FN). Finalmente, dentro de cada cajón organizas por color o uso (3FN). Cada paso reduce el desorden y hace más fácil encontrar las cosas.

Â¿Por qué normalizar?

Sin normalización, puedes tener estos problemas (anomalías):

  • Anomalía de inserción: No puedes agregar un dato sin agregar información innecesaria
  • Anomalía de actualización: Si un dato está repetido en 100 filas, debes actualizar las 100
  • Anomalía de eliminación: Al borrar un registro, pierdes información que no querías perder

Primera Forma Normal (1FN)

📄 Regla

Una tabla está en 1FN si:

  1. Todos los atributos contienen valores atómicos (indivisibles, un solo valor por celda)
  2. No hay grupos repetitivos (columnas que se repiten como Telefono1, Telefono2, Telefono3)
  3. Existe una llave primaria

✅ Ejemplo: Aplicar 1FN

✘ ANTES (viola 1FN):

Matricula Nombre Telefonos Materias
A001 Daniel García 555-1234, 555-5678 Matemáticas, Física, Programación

Problemas: "Telefonos" y "Materias" tienen múltiples valores en una celda.

✔ DESPUÁ‰S (en 1FN): Se separa en tablas independientes.

Tabla ALUMNOS:

Matricula (PK) Nombre
A001 Daniel García

Tabla TELEFONOS:

Matricula (FK) Telefono
A001 555-1234
A001 555-5678

Tabla INSCRIPCIONES:

Matricula (FK) Materia
A001 Matemáticas
A001 Física
A001 Programación

Segunda Forma Normal (2FN)

📄 Regla

Una tabla está en 2FN si:

  1. Ya está en 1FN
  2. Todos los atributos no-clave dependen de toda la llave primaria, no solo de una parte de ella (aplica especialmente a llaves compuestas)

Dicho de otro modo: No hay dependencias parciales.

✅ Ejemplo: Aplicar 2FN

✘ ANTES (viola 2FN): Tabla INSCRIPCIONES con llave compuesta

Matricula (PK) MateriaID (PK) NombreAlumno NombreMateria Calificacion
A001 MAT101 Daniel García Matemáticas I 85
A001 FIS201 Daniel García Física I 90
A002 MAT101 María López Matemáticas I 92

Problema:

  • "NombreAlumno" depende SOLO de Matricula (no de MateriaID) â†’ dependencia parcial
  • "NombreMateria" depende SOLO de MateriaID (no de Matricula) â†’ dependencia parcial
  • "Calificacion" depende de AMBAS (Matricula + MateriaID) â†’ correcto

✔ DESPUÁ‰S (en 2FN): Separar en 3 tablas

Tabla ALUMNOS: Matricula (PK), NombreAlumno

Tabla MATERIAS: MateriaID (PK), NombreMateria

Tabla INSCRIPCIONES: Matricula (PK,FK), MateriaID (PK,FK), Calificacion

💡 Truco para recordar 2FN

Si tu tabla tiene una llave primaria de una sola columna, y ya está en 1FN, automáticamente está en 2FN. Las dependencias parciales solo ocurren con llaves compuestas.

Tercera Forma Normal (3FN)

📄 Regla

Una tabla está en 3FN si:

  1. Ya está en 2FN
  2. No existen dependencias transitivas: ningún atributo no-clave depende de otro atributo no-clave

Dicho de otro modo: Cada atributo no-clave depende directamente de la llave primaria y de nada más.

✅ Ejemplo: Aplicar 3FN

✘ ANTES (viola 3FN):

Matricula (PK) Nombre CarreraID NombreCarrera Coordinador
A001 Daniel 1 Sistemas Dr. Ramírez
A002 María 1 Sistemas Dr. Ramírez
A003 Juan 2 Industrial Dra. Flores

Problema: "NombreCarrera" y "Coordinador" no dependen de Matricula directamente. Dependen de CarreraID (que no es la PK). Esto es una dependencia transitiva:

Matricula â†’ CarreraID â†’ NombreCarrera, Coordinador

✔ DESPUÁ‰S (en 3FN):

Tabla ALUMNOS:

Matricula (PK) Nombre CarreraID (FK)
A001Daniel1
A002María1
A003Juan2

Tabla CARRERAS:

CarreraID (PK) NombreCarrera Coordinador
1SistemasDr. Ramírez
2IndustrialDra. Flores

Ahora "NombreCarrera" y "Coordinador" dependen directamente de su propia PK (CarreraID). Sin redundancia.

Resumen rápido de normalización

Forma Normal Requisito principal Elimina
1FN Valores atómicos, sin grupos repetitivos Datos multivaluados en una celda
2FN Sin dependencias parciales Atributos que dependen solo de parte de la PK
3FN Sin dependencias transitivas Atributos no-clave que dependen de otros no-clave

💡 Frase para recordar (del informático Bill Kent)

"Cada atributo no-clave debe proporcionar un hecho sobre la llave (1FN), toda la llave (2FN), y nada más que la llave (3FN)."

Esta frase resume todo el proceso de normalización.

3.6 Herramientas CASE

📄 Definición

CASE (Computer-Aided Software Engineering) son herramientas de software que asisten en el diseño, modelado y generación de código para bases de datos. Permiten crear diagramas ER de forma visual y generar automáticamente los scripts SQL.

Â¿Qué hacen las herramientas CASE para BD?

  • Crear diagramas ER de forma visual (arrastrando entidades y conectando relaciones)
  • Generar SQL automáticamente a partir del diagrama (forward engineering)
  • Crear el diagrama a partir de una BD existente (reverse engineering)
  • Validar el modelo (verificar integridad, detectar errores de diseño)
  • Generar documentación y diccionarios de datos

Herramientas CASE populares

Herramienta Tipo Notas
MySQL Workbench Gratuita Modelado visual, genera SQL para MySQL. Ideal para aprender.
draw.io / diagrams.net Gratuita (web) Para diagramas ER simples. No genera SQL pero es fácil de usar.
Lucidchart Freemium (web) Diagramas ER colaborativos en la nube.
ERDPlus Gratuita (web) Específica para diagramas ER educativos. Genera SQL básico.
Oracle SQL Developer Data Modeler Gratuita Profesional, soporta modelo conceptual, lógico y físico.
Erwin Data Modeler Comercial Estándar de la industria para proyectos grandes.
dbdiagram.io Freemium (web) Escribes la estructura en texto y genera el diagrama visual.

💡 Recomendación para el curso

Si estás empezando, usa ERDPlus (erdplus.com) para crear tus diagramas ER de práctica. Es gratuito, online y está diseñado para estudiantes. Para trabajo más profesional, MySQL Workbench es la mejor opción gratuita con funcionalidad completa.

🔬 Analogía

Las herramientas CASE son como AutoCAD para los arquitectos. Puedes dibujar planos a mano en papel, pero un software te permite hacerlo más rápido, detectar errores, y generar automáticamente las especificaciones técnicas. No reemplazan tu conocimiento de diseño, pero lo hacen mucho más productivo.
