1.1 Definiciones y Conceptos Fundamentales

Antes de construir una casa, necesitas conocer los materiales: ladrillos, cemento, varillas. De la misma forma, antes de trabajar con bases de datos, necesitas dominar su vocabulario básico.

🏠 Analogía: La oficina de archivo

Imagina una oficina gubernamental con un gran archivero metálico. Cada cajón es un archivo, cada carpeta dentro del cajón es un registro, cada dato escrito en la carpeta es un campo, y todo el sistema de organización junto con las reglas para guardar y buscar carpetas es el sistema de base de datos.

Dato

📄 Definición

Un dato es la unidad mínima de información. Es un hecho aislado que por sí solo no tiene un significado completo. Puede ser un número, una palabra, una fecha o cualquier valor individual.

✅ Ejemplos de datos

  • 42 — ¿Es una edad? ¿Un número de calle? ¿Una calificación? Solo es un número.
  • "Daniel" — ¿Es un nombre? ¿Una ciudad? ¿Una marca? Solo es texto.
  • 2024-03-15 — ¿Fecha de nacimiento? ¿De venta? Solo es una fecha.

Los datos adquieren significado cuando les damos contexto. "Daniel" + "es el nombre del alumno" = información.

Información

📄 Definición

La información es el resultado de procesar, organizar y dar contexto a los datos. Es un dato (o conjunto de datos) con significado útil para quien lo recibe.

Datos crudos
→
Procesamiento + Contexto
→
Información útil

✅ Ejemplo

Datos: "Daniel", "García", "85", "Matemáticas"

Información: "El alumno Daniel García obtuvo 85 de calificación en Matemáticas"

Campo

📄 Definición

Un campo es la unidad más pequeña de datos con significado dentro de un registro. Representa una característica o atributo específico. En una tabla, un campo corresponde a una columna.

🔬 Analogía

En un formulario de inscripción, cada espacio para llenar es un campo: "Nombre: ___", "Apellido: ___", "Edad: ___". El campo define qué tipo de dato se espera.

Registro

📄 Definición

Un registro (también llamado tupla o fila) es un conjunto de campos relacionados que describen a una entidad completa. En una tabla, un registro corresponde a una fila.

✅ Ejemplo visual

ID (campo) Nombre (campo) Apellido (campo) Edad (campo)
1 Daniel García 22
2 María López 20
3 Juan Martínez 21

↑ Cada fila completa es un registro. Cada columna es un campo.

Archivo (en contexto de BD)

📄 Definición

Un archivo es un conjunto de registros del mismo tipo almacenados de forma organizada. En el contexto de bases de datos, un archivo equivale conceptualmente a una tabla.

🔬 Analogía

Si cada registro es una ficha de alumno, entonces el archivo es el cajón completo que contiene todas las fichas de alumnos. No mezclas fichas de alumnos con facturas; cada tipo tiene su propio cajón (archivo/tabla).

Banco de Datos

📄 Definición

Un banco de datos (o base de datos) es una colección organizada de datos relacionados entre sí, almacenados de forma estructurada para permitir su acceso, gestión y actualización de manera eficiente.

🔬 Analogía

El banco de datos es toda la biblioteca: incluye todos los estantes (tablas), todos los libros (registros) y el sistema de organización que los conecta. No es solo un cajón, sino todo el edificio con su lógica.

Sistema de Información

📄 Definición

Un sistema de información es el conjunto de componentes (personas, hardware, software, datos, procedimientos y redes) que trabajan juntos para recopilar, procesar, almacenar y distribuir información que apoya la toma de decisiones en una organización.

Sistema de Base de Datos

📄 Definición

Un sistema de base de datos es un sistema computarizado cuyo propósito es almacenar información y permitir a los usuarios recuperar y actualizar esa información con base en peticiones. Incluye cuatro componentes principales:

  1. Datos: La información almacenada
  2. Hardware: Los discos, servidores, memoria
  3. Software: El DBMS (Sistema Manejador de Base de Datos)
  4. Usuarios: Administradores, programadores, usuarios finales

1.2 Evolución de las Bases de Datos

Las bases de datos no siempre fueron como las conocemos hoy. Han pasado por varias generaciones, cada una resolviendo problemas de la anterior.

1950s-1960s: Procesamiento de archivos

Los datos se almacenaban en archivos planos en cintas magnéticas. Cada programa tenía sus propios archivos. Si dos programas necesitaban los mismos datos, se duplicaban. Problemas: redundancia, inconsistencia y dependencia de los datos respecto al programa.

1960s-1970s: Modelo Jerárquico

Los datos se organizan en estructura de árbol (padre-hijo). El ejemplo más famoso es IMS de IBM (1966). Ventaja: rápido para relaciones padre-hijo. Desventaja: inflexible, difícil navegar relaciones complejas.

1970s: Modelo de Red (CODASYL)

Extiende el modelo jerárquico permitiendo que un hijo tenga múltiples padres (grafo en lugar de árbol). Más flexible pero extremadamente complejo de programar y mantener.

1970: Modelo Relacional (E.F. Codd)

En 1970, Edgar F. Codd publica su artículo revolucionario proponiendo organizar los datos en tablas (relaciones) con filas y columnas. Introdujo el álgebra relacional como lenguaje de consulta. Este modelo es la base de las BD modernas.

1980s: RDBMS comerciales

Aparecen los primeros sistemas comerciales: Oracle (1979), DB2 de IBM (1983), SQL Server. Se estandariza el lenguaje SQL (1986, ANSI). Las bases de datos relacionales dominan el mercado.

1990s: Bases de datos orientadas a objetos

Intentan combinar BD con programación orientada a objetos. Surgen las bases de datos objeto-relacionales (PostgreSQL). También nace la web y crece la demanda de BD para aplicaciones en internet.

2000s-presente: NoSQL y NewSQL

Con el Big Data surgen alternativas: MongoDB (documentos), Redis (clave-valor), Neo4j (grafos). No reemplazan al modelo relacional, sino que lo complementan para casos específicos de alto volumen o datos no estructurados.

🔬 Analogía: Evolución del almacenamiento

Es como la evolución de guardar música: Vinnil (archivos secuenciales) → Casete (jerárquico) → CD (relacional, acceso directo a cualquier canción) → Streaming (distribuido, en la nube). Cada paso resolvió limitaciones del anterior.

1.3 Las 12+1 Reglas de Codd

En 1985, Edgar F. Codd publicó 12 reglas (numeradas del 0 al 12, por eso son 13) que definen qué debe cumplir un sistema para ser considerado un verdadero Sistema de Gestión de Bases de Datos Relacional (RDBMS). Son como un "examen de certificación" para un DBMS.

💡 ¿Por qué importan?

Ningún RDBMS comercial cumple las 12 reglas al 100%. Pero son el estándar ideal al que aspiran. Te ayudan a entender qué características debe tener una BD relacional "pura".

# Regla Explicación sencilla
0 Regla fundamental Un RDBMS debe gestionar los datos únicamente usando sus capacidades relacionales (tablas, filas, columnas).
1 Regla de la información Toda la información debe representarse como valores en tablas. No hay "datos ocultos" fuera de las tablas.
2 Regla del acceso garantizado Cada dato individual debe ser accesible usando: nombre de tabla + nombre de columna + valor de llave primaria.
3 Tratamiento de valores nulos El sistema debe soportar valores NULL para representar información faltante o no aplicable, de forma consistente.
4 Catálogo en línea basado en el modelo relacional La estructura de la BD (metadatos: nombres de tablas, columnas, tipos) debe almacenarse también en tablas consultables con SQL.
5 Sublenguaje completo Debe existir al menos un lenguaje (SQL) que soporte: definición de datos, manipulación, seguridad, integridad y transacciones.
6 Actualización de vistas Las vistas (consultas guardadas) que sean teóricamente actualizables deben poder ser actualizadas por el sistema.
7 Inserción, actualización y eliminación de alto nivel Se debe poder insertar, actualizar y borrar conjuntos de filas en una sola operación (no solo fila por fila).
8 Independencia física Cambiar cómo se almacenan físicamente los datos (disco, índices) no debe afectar a las aplicaciones que los usan.
9 Independencia lógica Cambiar la estructura lógica (agregar columnas, renombrar) no debe obligar a reescribir las aplicaciones existentes.
10 Independencia de integridad Las reglas de integridad (restricciones) deben definirse en la BD, no en las aplicaciones. Si cambias una regla, solo la cambias en un lugar.
11 Independencia de distribución Si la BD se reparte en varios servidores, el usuario no debería notarlo. Las consultas funcionan igual.
12 No subversión Si el sistema tiene un lenguaje de bajo nivel, este no debe poder saltarse las reglas de integridad y seguridad definidas en el nivel relacional.

🔬 Analogía: Reglas de un buen restaurante

Las reglas de Codd son como las normas de sanidad para un restaurante. Si un restaurante cumple todas, es excelente. Si cumple la mayoría, es bueno. Pero si no cumple las básicas (como la regla 1: toda la información en tablas), no puede llamarse "restaurante relacional". Los RDBMS como MySQL, PostgreSQL y Oracle cumplen la gran mayoría.

Las 3 reglas más importantes para recordar

🌟 Enfócate en estas

  1. Regla 1 (Información): Todo son tablas. Si no está en una tabla, no existe para la BD.
  2. Regla 2 (Acceso garantizado): Cualquier dato se localiza con: tabla + columna + llave primaria.
  3. Regla 8 y 9 (Independencia): Los cambios internos no rompen las aplicaciones. Esto es lo que hace a las BD relacionales tan poderosas y duraderas.
